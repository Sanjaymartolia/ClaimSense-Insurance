ClaimSense: Auditable Health-Insurance Claim Adjudication with Agents, Tested Code and Human Approval

Technical workflow paper · Agentic AI Capstone · Team of six · Version 0.1 (27 Oct 2026)

Abstract

ClaimSense helps a claims adjudicator settle hospitalisation claims under the IRDAI-standard Arogya Sanjeevani policy. The system reads a claim packet (claim form, discharge summary, itemised bill, policy schedule), extracts every bill line with its source span, retrieves the governing policy clause for each line, and computes every rupee in unit-tested code. These amounts cover room-rent caps, proportional cuts to linked charges, sub-limits, non-payable items and co-pay. A fraud analyst and a critic check the worksheet before a human approves it. The approval is bound to a hash of the exact worksheet, so any edit invalidates it. Adjudicator corrections become reviewed lessons in a playbook that improves later runs. This paper describes the architecture, the end-to-end request workflow, the engineering workflow for a six-person team, the evaluation protocol and the path to a production-ready deployment.

Design principle. The model proposes; code and people decide.

Signature challenges.

  • A. Money you can audit. Every rupee comes from tested code, and every deduction cites a clause.
  • B. A playbook that learns from adjudicators. A Reflexion loop learns from adjudicator edits, with a human approving each lesson.

Graph state (typed): claim, plan, worksheet, critic_report, fraud_flags, approval, messages, budget_used. The SQLite checkpointer persists state after every node, so a run can be stopped mid-claim and resumed (L8 evidence). When the adjudicator edits a line, the graph re-enters at the calculator and critic, and the old approval token becomes invalid.

Replanning (L10). If a tool result contradicts the plan (for example, the policy was not active on the admission date), the planner revises the plan. The admissibility failure then short-circuits line-item adjudication, and the trace records the replan.

4. Money you can audit (Signature A)

All amounts are Decimal, rounded half-up to paise, computed only in src/claimsense/calc/.

Room-rent limit per day

eligible_room = min(room_rent_pct × sum_insured, room_rent_max_per_day)

Proportional cut. When the actual room rent exceeds the eligible limit, the linked charges are paid in proportion:

ratio = eligible_room / actual_room_per_day
payable_linked_line = line_amount × ratio

Which categories count as "linked" (and which are excluded, such as pharmacy and implants under IRDAI norms) must be confirmed from the exact wording and cited by clause.

Worked illustration (hypothetical numbers for the unit tests; confirm against the wording): sum insured ₹3,00,000 gives 2% = ₹6,000, capped at ₹5,000/day. Actual room rent is ₹7,000/day for 3 nights.

Invariants enforced by the contracts (src/claimsense/contracts/worksheet.py):

  • Each line: claimed − Σ deductions = payable.

5. Human control (L14)

  • interrupt() pauses the graph and shows the exact worksheet with three options: approve, edit

a line, or reject.

  • ApprovalToken stores claim_id and sha256(worksheet JSON). settle_claim refuses any

token where token.is_valid_for(current_worksheet) is false.

  • Two approval levels apply above approval.senior_threshold_inr (in config/models.yaml) or

when a fraud flag is set.

  • Hooks: a pre-tool hook checks the per-agent tool allow-list and the budget (tool calls, cost).

A post-tool hook writes a trace entry with health data scrubbed.

Demo. Edit one line, the totals recalculate, and the earlier approval no longer works.

6. A playbook that learns (Signature B, L12)

  1. Run the pipeline on development claims only.
  2. Score each run with checker code: amounts, clause existence, DB state. A judge scores only what code cannot check.
  3. A reflection step turns each failure, adjudicator edit or critic rejection into a Lesson: a short rule, applies_when, and the related clause IDs.
  4. An adjudicator approves or rejects each lesson. Rejections record a reason, and the brief requires at least one rejected example.
  5. The coverage analyst retrieves only approved, relevant lessons. Any lesson can be withdrawn.
  6. Freeze the playbook before the held-out run. Measure settlement error and edit rate before and after (E3, 3 repeats), and identify lessons that made results worse.

The suite needs 30+ attacks, including injection through our own data path. E2 reports attack success with defences off and on, and the false-block rate on clean claims. The threat model is one page, kept in a private location.

8. Evaluation protocol (L13)

  • Golden set: 80 synthetic claims, split into about 20 development and 60 held-out cases.

Expected worksheets are computed by hand before the agent runs. The case mix covers room-rent breaches, unserved waiting periods, duplicate bills, non-payable consumables, sub-limits partly used by earlier claims, and admissions outside the policy period. Held-out cases live outside the repo, and Claude Code is denied access to them.

  • Checks: code first (amounts, cited clause exists, final DB state, tool calls, forbidden

actions). An LLM judge from a different model family scores explanation quality. The judge is calibrated on 20+ human labels, with agreement reported as Cohen's κ.

  • Retrieval: Recall@5 on 30+ labelled bill-line queries, measured before and after one change.
  • Experiments (one harness, each experiment a config file):
IDQuestionConfigurations
E1Does the agent justify its cost?C0 fixed workflow · C1 single agent · C2 team (same model, tools, budget)
E2Do the defences work?Defences off / on: attack success and false blocks
E3Did the lessons help?Held-out before / after playbook, × 3 repeats, with lesson cost
E4Signature ablationLLM arithmetic vs calculator, error in ₹

For every configuration, report task success, policy violations, attack success, false blocks, cost per case, p50/p95 latency and errors, including failed and timed-out runs.

9. Deployment and operations (L16)

  • docker compose up starts the API, the MCP servers (HTTP), Chroma, Prometheus and Grafana.
  • config/models.yaml is the single versioned place for model IDs, prompts, budgets and thresholds.
  • CI (GitHub Actions): lint (ruff) → unit tests (pytest) → eval gate on the dev set, which

fails below the threshold. A Discord webhook fires on failure.

  • Dashboard: claims processed, adjudicator edit rate, ₹ deducted by reason, fraud flags,

turnaround, cost per claim. Alert: the edit rate rises (drift).

  • Production-ready checklist:

- clean-machine install from the README - secrets only in .env and GitHub Secrets, with secret scanning on - masked traces - one alert tested - one failed CI run explained

10.2 Per-task loop (with Claude Code)

  1. Pick a task ID from the tracker or the GitHub issue (for example, T15). Create a branch named t15-calculator.
  2. Plan in Claude Code plan mode: "Read issue T15, CLAUDE.md and contracts/. Plan the change. Don't write code yet." A human reviews and corrects the plan. This is design evidence.
  3. Test first. The human writes the key test cases (hand-worked amounts with clause references).
  4. Implement with Claude until the tests pass. The project hook auto-formats with ruff.
  5. Review. Run /code-review locally, then open a PR using the template. A reviewer from another role responds within 24 hours.
  6. Merge after CI passes. Update the tracker row and CONTRIBUTIONS.md with the PR link.

CLAUDE.md encodes the non-negotiable rules for every teammate's Claude session: money only in calc/, document text is data, exact-payload approval, no secrets or real data, and no access to held-out cases. .claude/settings.json denies reading .env and the held-out folder.

13. Questions the viva will ask

  1. Trace one claim through Figure 1. Which boxes did it pass through, and what did each decide?
  2. Which decisions were made by the model, and which by code, rules or a person?
  3. What did the team of agents add over the single-agent baseline, and at what cost?
  4. Which experiment changed the design?
  5. Show traces for missing evidence, a failed tool and an injected instruction.
  6. What does memory retain, why, and how is it deleted?
  7. Which lessons helped on unseen claims, and how do you know?
  8. What would be required before a supervised pilot with real users?
